# Audit Log Implementation Plan

**Goal:** Record every write action against a case file so support can answer "who changed this and when".
**Architecture:** A `AuditLogService` writes append-only rows through the existing TypeORM connection; an interceptor on the mutating controller routes calls it. No new dependencies — the entity lives alongside the existing `src/cases/` module.
**Requirements source:** Support team's escalation doc, 2026-07-18.
**Plan status:** in-progress

### Ticket 2.2: Retention pruning job

- **Status:** done
- **Size:** M
- **Complexity:** moderate
- **Agent tier:** `sonnet`
- **Escalation:** `haiku` ×3 → re-dispatched at `sonnet`
- **Depends on:** Ticket 2.1
- **Needs approval:** none
- **Files:**
  - Create: `src/audit/audit-retention.service.ts`
  - Modify: `src/audit/audit.module.ts`
  - Test: `src/audit/audit-retention.service.spec.ts`

**Context:** Rows in `audit_log` older than 400 days are deleted on a daily schedule. The app already uses `@nestjs/schedule`, registered in `src/app.module.ts` — use `@Cron` from it rather than adding a scheduler. `AuditLogService` (from Milestone 1) exposes the TypeORM repository as `this.repo`; the retention service should take its own injected repository rather than reaching through the service. Delete in batches of 1000 so a large backlog doesn't hold a single long transaction open.

**Acceptance criteria:**

- [x] Rows older than 400 days are deleted; newer rows are untouched
- [x] Deletion runs in batches of at most 1000 rows
- [x] The retention window is read from config, not hardcoded at the call site
